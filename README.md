# Спасибо-бот

## Описание проекта

Личный Telegram-бот для «спасибо» между близкими людьми, написанный на Swift (Vapor 4).
Изначально это был корпоративный Kudos Bot; теперь он перенастроен для домашнего использования
(на двоих, но без ограничения на число участников) и работает на домашнем сервере под Ubuntu.

Бот работает полностью внутри Telegram, без веб-интерфейса, и умеет:

- передавать «спасибо» в пару нажатий — если получатель один, выбирать его не нужно;
- присылать получателю уведомление с кнопками-реакциями ❤️ 🤗 🥹 — отправитель видит ответ;
- показывать ленту последних «спасибо» прямо в чате;
- доставать случайное «спасибо» из «банки благодарностей»;
- показывать личную статистику и выгружать свои «спасибо» в CSV;
- напоминать о себе в личных сообщениях (только тем, кто сегодня ещё не говорил спасибо);
- присылать итоги недели по воскресеньям;
- пускать только своих: доступ по списку участников, приглашение через код `/link`.

### Технологическая основа

- **Backend:** Swift + Vapor 4  
- **База данных:** PostgreSQL  
- **Архитектура:** feature-folder (BotMenu, Employees, Kudos, Reminders, Core)  
- **Контейнеризация:** Docker + Docker Compose  
- **Продакшен:** VPS (Ubuntu), деплой через Docker  
- **CI/CD:** GitHub Actions (тесты → сборка Docker-образа → деплой на сервер)  
- **Тестовая среда:** отдельная тестовая БД (`kudos_test`) + unit/integration тесты  


### Инструкции для ИИ и контрибьюторов

В репозитории есть файл `AGENTS.md` с правилами и ограничениями по архитектуре и стилю кода.  
Он нужен, чтобы ИИ-ассистенты и новые участники команды писали изменения в одном стиле и соблюдали принятые архитектурные договоренности.


## Основные возможности

Главное меню — один экран:

| Кнопка | Что делает |
|---|---|
| 💌 Сказать спасибо | Сценарий благодарности. Если других участников один — сразу просит текст, иначе показывает список. Минимум 3 символа: «спасибо за ужин» — тоже спасибо. |
| 📜 Наши спасибо | Последние 10 «спасибо», где ты отправитель или получатель, с датами и реакциями. |
| 🫙 Вспомнить | Случайное «спасибо» из полученных — «банка благодарностей». |
| 📊 Статистика | Отправлено / получено (всего и за неделю), сколько реакций получили твои «спасибо». Тут же выгрузки в CSV. |
| ⚙️ Настройки | Только для администратора: участники, привязка Telegram, полный экспорт. |

Получатель видит уведомление с кнопками ❤️ 🤗 🥹. Реакцию можно поставить один раз; отправитель получает сообщение
«❤️ Саша ответил(а) на твоё спасибо», а реакция появляется в ленте.

### BotMenu: сценарии и навигация

Ранее логика меню находилась в одном большом файле `BotMenuController.swift`.  
Теперь она разделена на несколько файлов-расширении по зонам ответственности: главный роутер (switch по `SessionState`), сценарии благодарности, статистика, админка (меню, участники, привязка Telegram) и UI-хелперы (пагинация и списки).  

### Сессии и состояния диалога

Бот хранит состояние диалога (`SessionState`) в базе данных (таблица `sessions` через Fluent), а не в памяти.
Это позволяет не терять прогресс сценариев при перезапуске приложения или контейнера: после рестарта бот продолжает диалог с пользователем с последнего шага.

Хранимые поля включают текущее состояние и черновики (например выбранного участника, страницу пагинации и т.д.).

### Участники

> В коде и базе участники по-прежнему хранятся как `Employee` / таблица `employees` — это историческое имя,
> переименование потребовало бы миграции живой базы без пользы для пользователей. В интерфейсе бота везде «участник».

- Источник правды по участникам — база данных, управляемая через «⚙️ Настройки» в Telegram.
- CSV-файл `Resources/SeedData/employees.csv` используется только для разового массового импорта и по умолчанию не применяется при старте.
- Чтобы включить импорт при старте, установите переменную окружения: `EMPLOYEES_CSV_IMPORT_ON_BOOT=1`.
- Режим импорта безопасный: CSV **только добавляет** отсутствующих участников и **не** обновляет существующих и **не** деактивирует тех, кого нет в CSV.
- Каждая запись содержит:
  - имя участника (как подписывать в боте),
  - статус активности (Да/Нет),
  - Telegram ID для связи с ботом и отправки личных уведомлений о новых благодарностях.
- Если получателей несколько, пользователь выбирает его из постраничного списка (себя в списке нет); если получатель один — шаг выбора пропускается.
- Если в базе есть участники с одинаковым ФИО, бот автоматически добавляет к кнопкам суффикс `(N)` (например: `Иванов Иван (1)`, `Иванов Иван (2)`), чтобы выбор всегда был однозначным.

- В общем каталоге для выбора получателя показываются только участники с заполненным `telegram_id`.
  Участники без `telegram_id` не видны обычным пользователям, пока администратор не выполнит привязку.
  Это защищает от ситуации, когда в списке появляется человек, который еще не начал пользоваться ботом.

### Доступ и роли

- Бот обрабатывает только личные чаты в Telegram. Сообщения из групп и каналов игнорируются.
- Обычный пользователь получает доступ к боту только если:
  - его `telegram_id` есть в таблице `employees`,
  - флаг `is_active = true`.
- Если участник не найден или неактивен, бот возвращает вежливое сообщение о том, что доступ ограничен.
- Администраторы всегда получают доступ, даже если их нет в `employees`. Админ определяется по:
  - `ADMIN_IDS` — список Telegram ID через запятую,
  - `ADMIN_USERNAMES` — список имён пользователей (без `@`) через запятую.

### Временные токены привязки (pending links)

Для безопасной привязки Telegram-аккаунтов используется механизм временных токенов.

Администратор может выдать участнику одноразовый код, который участник отправляет боту в личном чате командой:

```
/link 123456
```

В админ-панели бот формирует эту команду в формате `code`, чтобы ее было удобно переслать и скопировать.

Код действует 6 часов. Просроченные или использованные записи автоматически очищаются планировщиком `PendingLinksScheduler` (периодическое обслуживание раз в 10 минут).

- При добавлении участника администратор создает временную запись привязки (`pending_link`) с одноразовым токеном.
- Код (токен) передается участнику и используется для подтверждения привязки через команду "/link" в личном чате с ботом.
- Код действует 6 часов и автоматически удаляется планировщиком после истечения срока или использования.
- После успешной привязки Telegram:
  - `telegram_id` сохраняется в таблице `employees`,
  - временный токен удаляется и не может быть использован повторно.
- Механизм защищает от случайной или ошибочной привязки чужого Telegram-аккаунта.

### Авто-очистка непривязанных участников

- Если участник был создан, но `telegram_id` не привязан в течение 24 часов, бот автоматически удаляет такого участника из таблицы `employees`.
- Перед удалением выполняется защита: если у участника есть хотя бы одна запись в `kudos` (как отправитель или получатель), он не удаляется.
- Очистка запускается планировщиком раз в 10 минут вместе с обслуживанием `pending_links`.

### Связи и подсчёт статистики

- Благодарности хранятся с привязкой к участникам через внешние ключи (`employee_id`, `from_employee_id`), а не просто к никам.
- Это обеспечивает корректный подсчёт статистики и экспорт данных даже при изменении никнеймов.
- Еще есть механика, чтобы при отсутствии Telegram ID используется резервный поиск по нику, но пока закомментировано в коде, чтобы не мешалось.
- Меню «Статистика» и персональные экспорты учитывают FK-связи между благодарностями и участниками.

### Экспорт CSV

- Экспортированные данные содержат фамилию и имя отправителя / получателя, а не только их логины.
- Пример структуры CSV:

  ```
  Дата и время;От кого (логин);От кого (имя);Кому (имя);Причина
  ```

### Персональный экспорт для участников

Каждый участник может самостоятельно выгрузить свои данные через меню бота:

- «Статистика»
  - «📤 Выгрузить отправленные» — CSV со всеми «спасибо», которые участник отправил;
  - «📥 Выгрузить полученные» — CSV со всеми «спасибо», которые участник получил.

Экспорт формируется автоматически и отправляется пользователю в виде файла прямо в Telegram.

### Напоминания (в личные сообщения)

Модуль `Reminders` пишет **каждому участнику в ЛС** в заданное время. Если человек сегодня уже сказал спасибо — его не беспокоим.

- **Тексты** — `Resources/Reminders/messages.json` (массив строк).
  Плейсхолдер `{name}` заменяется на имя второго участника, если он один; при большем числе участников такие тексты пропускаются.
- **Когда** — `REMINDER_TIMES` в формате `HH:mm` через запятую, например `REMINDER_TIMES=21:00`.
  Если переменная пуста или закомментирована — напоминания выключены.
- Время считается по часовому поясу контейнера (`TZ`, по умолчанию `Europe/Moscow` в `docker-compose.prod.yml`).

Старая переменная `REMINDER_CHAT_ID` больше не используется.

### Итоги недели

Модуль `Digest` по воскресеньям присылает каждому участнику итоги последних 7 дней:
сколько «спасибо» ты сказал(а) и получил(а), плюс одно случайное полученное «спасибо» недели.

- `WEEKLY_DIGEST_TIME` — время отправки `HH:mm` (по умолчанию `20:00`);
- `WEEKLY_DIGEST_TIME=off` — выключить итоги.

> ⚠️ **Важно при изменении `.env`.** Файл `.env` подключается через `env_file` и читается только в момент **создания** контейнера. Чтобы изменения применились, контейнер нужно **пересоздать**:
>
> ```bash
> docker compose -f docker-compose.prod.yml up -d --force-recreate kudos-bot
> ```
>
> Проверить в логах:
>
> ```bash
> docker compose -f docker-compose.prod.yml logs --tail=30 kudos-bot | grep -iE "remind|digest"
> ```
>
> Не используйте `down -v` — это удалит том с базой.

## Данные и структура базы

- PostgreSQL база данных запускается как сервис `db` в Docker Compose и использует volume для хранения данных.
- Таблица участников содержит данные из CSV-семпла.
- Таблица благодарностей хранит информацию с FK-связями на участников.
- Экспортированные CSV-файлы сохраняются в папке `exports/` на хост-машине (примонтировано как `./exports:/exports`).

## Тесты и тестовая среда

В проекте есть unit- и integration-тесты, которые проверяют:

- запуск приложения и выполнение миграций;
- работу репозитория участников (поиск, пагинация);
- построение клавиатуры Telegram-меню (кнопки, разметка, роли);
- экспорт благодарностей в CSV (формат файла, BOM, разделители и содержимое);
- сервис благодарностей: статистику, ленту, банку, реакции и итоги недели;
- тексты напоминаний и форматирование сообщений.

### Тестовая база данных локально

Для тестов используется отдельная база `kudos_test`, которая поднимается через `docker-compose.test.yml`:

```yaml
services:
  db_test:
    image: postgres:16-alpine
    ports:
      - "5433:5432"
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: kudos_test
```

Во время локальных тестов приложение запускается в окружении `.testing` и по умолчанию подключается к `postgresql://postgres:postgres@localhost:5433/kudos_test?sslmode=disable`.

Если задана переменная окружения `DATABASE_URL`, она имеет приоритет во всех режимах — это используется в CI.

### Запуск тестов локально

1. Поднять тестовую базу:

   ```bash
   docker compose -f docker-compose.test.yml up -d
   ```

2. Запустить тесты:

   ```bash
   swift test
   ```

   Если в корне проекта лежит `.env` с `DATABASE_URL` для прода, Vapor подхватит его и в тестах.
   Тогда передайте адрес тестовой базы явно:

   ```bash
   DATABASE_URL="postgresql://postgres:postgres@localhost:5433/kudos_test?sslmode=disable" swift test
   ```

В `.github/workflows/deploy.yml` есть стадия **Run Unit & Integration Tests**:

- Runner: `ubuntu-22.04`.
- Swift устанавливается через `swift-actions/setup-swift@v1` с версией `5.9`.
- Поднимается сервис PostgreSQL с базой `kudos_test` на порту `5432`.
- Тесты запускаются командой `swift test`, при этом в окружении передаётся:

  ```bash
  DATABASE_URL=postgresql://postgres:postgres@localhost:5432/kudos_test?sslmode=disable
  ```

Если тесты не проходят, дальнейшие стадии (`build-and-push` и `deploy`) не выполняются, поэтому продакшен остается в прежнем стабильном состоянии.

## Развёртывание

### Локальный запуск

**Требования:** Xcode 15+/Swift 5.10, Docker Desktop.

Запуск через Docker Compose:

```bash
docker compose up --build -d
docker compose logs -f
```

### Продакшен

- Развёртывание на VPS (Ubuntu 22/24) с Docker и Docker Compose.
- Папка приложения `/apps/kudos-bot`.
- Файл окружения `.env` с настройками бота, базы данных и администраторами.
- Пример `.env`:

  ```env
  BOT_TOKEN=ваш_токен_бота

  POSTGRES_DB=kudos
  POSTGRES_USER=postgres
  POSTGRES_PASSWORD=postgres
  POSTGRES_HOST=db
  POSTGRES_PORT=5432
  DATABASE_URL=postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@${POSTGRES_HOST}:${POSTGRES_PORT}/${POSTGRES_DB}?sslmode=disable

  ADMIN_IDS=12345678,12345678

  # Личные напоминания (HH:mm через запятую). Пусто — выключены.
  REMINDER_TIMES=21:00

  # Итоги недели по воскресеньям (HH:mm, по умолчанию 20:00). off — выключить.
  # WEEKLY_DIGEST_TIME=20:00

  # Опционально: синхронизация участников из CSV при старте (create-only)
  # По умолчанию выключено. Не обновляет и не удаляет существующих.
  # EMPLOYEES_CSV_IMPORT_ON_BOOT=1

  # Опционально: пороги healthz для Telegram polling
  # POLLING_STALE_SECONDS=120
  # HEALTH_STARTUP_GRACE_SECONDS=120

  ```

- Для запуска на VPS:

  ```bash
  sudo mkdir -p /apps/kudos-bot && cd /apps/kudos-bot
  sudo nano .env  # добавить переменные окружения
  sudo chmod 600 .env
  ```

- Запуск через Docker Compose с продовым файлом:

  ```bash
  docker compose -f docker-compose.prod.yml up -d
  ```

## Массовый импорт участников на VPS (опционально)

Источник правды по участникам — админ-панель в Telegram. CSV нужен только для разового массового добавления участников (например, при первом запуске или при переносе базы).

### Вариант 1 (рекомендуется): через флаг импорта при старте

1. Подготовить CSV на сервере в `/apps/kudos-bot/Resources/SeedData/employees.csv` (формат как в `employees.template.csv`).
2. В `.env` временно добавить:

```env
EMPLOYEES_CSV_IMPORT_ON_BOOT=1
```

3. Перезапустить контейнер бота:

```bash
docker compose -f docker-compose.prod.yml up -d --no-deps --build kudos-bot
```

После импорта можно удалить переменную `EMPLOYEES_CSV_IMPORT_ON_BOOT`, чтобы при следующих рестартах импорт не выполнялся.


## Примечания

- Админ-панель является источником правды по участникам. CSV используется только для разового импорта (create-only) и не деактивирует существующих участников.
- Скрипт `Scripts/sync_employees.sql` можно использовать только как разовую утилиту миграции/починки и запускать осознанно (он может менять данные в БД).
- Для аварийного полного сброса (reset) можно использовать TRUNCATE, но это редко нужно.


## CI/CD и мониторинг

### CI/CD

- Автоматическая сборка и пуш Docker-образа в Docker Hub при пуше в ветку `main`.
- Теги образа: `latest` и SHA коммита.
- SSH-доступ к VPS для обновления контейнеров через `docker compose pull && docker compose up -d`.
- Пайплайн настроен в `.github/workflows/deploy.yml`.

### Мониторинг и healthcheck

- Эндпоинт `/health` — простой liveness-check (приложение поднято и отвечает HTTP).
- Эндпоинт `/healthz` — расширенный healthcheck для продового мониторинга.
  Проверяет:
  - доступность БД,
  - живость Telegram polling-loop.
- `/healthz` возвращает:
  - HTTP `200`, если БД и polling в норме;
  - HTTP `503`, если есть деградация.

- Примеры проверки:

  ```bash
  curl -i http://127.0.0.1:8080/health
  curl -i http://127.0.0.1:8080/healthz
  ```

- Настройка мониторинга (например, Uptime Kuma):

  - Тип: HTTP(s)
  - URL: `http://<IP_VPS>:8080/healthz`
  - Метод: GET
  - Интервал: 60 секунд
  - Таймаут: 10–15 секунд
  - Попытки: 2–3
  - Допустимые коды: только `200`
  - Авторизация: отсутствует

- Пороговые параметры (опционально через `.env`):

  ```env
  POLLING_STALE_SECONDS=120
  HEALTH_STARTUP_GRACE_SECONDS=120
  ```

- В `docker-compose.prod.yml` используется `autoheal`: контейнеры с label `autoheal=true`
  автоматически перезапускаются при `unhealthy`.

### Runbook при деградации

Если в Uptime Kuma монитор по `/healthz` ушел в DOWN, используйте короткий чек-лист:

1. Проверить статус контейнеров:

```bash
cd /apps/kudos-bot
docker compose -f docker-compose.prod.yml ps
```

2. Проверить текущий health:

```bash
curl -i http://127.0.0.1:8080/healthz
```

3. Посмотреть последние логи бота и autoheal:

```bash
docker logs --since=15m kudos-bot
docker logs --since=15m autoheal
```

4. Если `kudos-bot` нестабилен (частые ошибки polling/рестарты), выполнить ручной перезапуск:

```bash
docker compose -f docker-compose.prod.yml restart kudos-bot
```

5. Если недоступен весь VPS (SSH/команды не отвечают), локальный autoheal не сработает — нужен reboot через панель или API VPS-провайдера.

### Очистка данных в базе

Для полной очистки таблицы благодарностей и сброса счетчика ID используйте команду:

```bash
docker compose exec -it db \
  psql -U postgres -d kudos -c \
  "TRUNCATE TABLE public.kudos RESTART IDENTITY CASCADE;"
```

**Внимание:** эта операция необратима и удалит все записи.

## Ручное создание и управление бэкапами

Для сохранения состояния базы данных на VPS можно создать SQL‑бэкап вручную.

### Создание бэкапа

Выполнить команды на сервере в директории `/apps/kudos-bot`:

```bash
docker exec -t kudos-db \
  pg_dump -U postgres -d kudos \
  > kudos_backup_$(date +%F_%H-%M).sql
```

После выполнения в каталоге появится файл вида:

```
kudos_backup_2025-11-27_13-58.sql
```

### Рекомендации

- Хранить 1–2 последних бэкапа, старые файлы можно удалять.
- Для удаления старых бэкапов:

```bash
rm kudos_backup_2025-*.sql
```

### Восстановление из бэкапа

Чтобы восстановить базу:

```bash
docker cp backup.sql kudos-db:/backup.sql
docker exec -it kudos-db \
  psql -U postgres -d kudos -f /backup.sql
```

## Администрирование бота

Кнопка «⚙️ Настройки» в главном меню видна только администраторам (`ADMIN_IDS` или `ADMIN_USERNAMES`).

### Возможности настроек

#### 1. Добавление участника

1. **Имя** — как подписывать человека в боте (можно ласковое прозвище).
2. **Привязка Telegram** — переслать любое сообщение от этого человека или нажать «🔗 Привязать через код»
   и отправить ему приглашение `/link <код>`. Код одноразовый и действует 6 часов.
3. После привязки участник получает доступ к боту. Непривязанные записи без «спасибо» удаляются через 24 часа.

#### 2. Отключение участника
«🚫 Отключить участника» скрывает человека из списков и останавливает напоминания, история «спасибо» сохраняется.

#### 3. Отключённые (восстановление и удаление)
- **✅ Восстановить** — вернуть участника.
- **🗑 Удалить совсем** — удалить участника и все связанные «спасибо» (с подтверждением).

#### 4. Полный экспорт
Кнопка «📊 Экспорт CSV» выгружает все «спасибо» за всё время.
